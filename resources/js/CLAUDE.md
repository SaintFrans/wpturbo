# Frontend conventions (`resources/js/`)

Inertia v3 + React 19 + TypeScript + Tailwind 4. The root [CLAUDE.md](../../CLAUDE.md) has
the working method; this file covers the frontend.

Activate the `inertia-react-development` skill for Inertia client-side patterns and the
`wayfinder-development` skill when wiring frontend calls to backend routes.

## Layout

| Directory                   | Contains                                                                           |
| --------------------------- | ---------------------------------------------------------------------------------- |
| `pages/`                    | Inertia page components. Path mirrors the string in `Inertia::render()`            |
| `layouts/`                  | The shells, **flat — one layout, one file**: app, content, section, auth, settings |
| `components/shell/`         | The menu bar and what only it uses: header, search, tabs, logo                     |
| `components/organizations/` | The Settings area's modals: create, delete, member and invitation                  |
| `components/clients/`       | The Clients area's modals                                                          |
| `components/account/`       | Account settings: passkeys, two-factor, delete account                             |
| `components/`               | Only what **every** domain uses: alert-error, empty-state, input-error, …          |
| `components/ui/`            | shadcn primitives on the React Aria base. Check here before writing a new one      |
| `hooks/`                    | Shared React hooks                                                                 |
| `types/`                    | Hand-maintained shared types                                                       |
| `actions/`, `routes/`       | **Generated by Wayfinder — never hand-edit**                                       |

Files are kebab-case. Components are named exports in PascalCase.

**A new resource domain gets its own directory** under `components/` (ADR-045). The root is the
shared set and should stay short enough to read in one glance.

**A component with one caller lives in that caller.** `SectionNav` and the sidebar collapse button
are inside `section-layout`; the account menu inside `app-header`; `PasskeyItem` and
`PasskeyRegistration` inside `manage-passkeys`. Extract a file when a _second_ caller appears, not
in anticipation of one — splitting early buys a prop interface between two halves of one
component, and it is how this app ended up with an unreachable sidebar template and a
`use-flash-toast` hook nothing called.

## Non-negotiables

### Never hand-edit generated code

`actions/` and `routes/` are Wayfinder output. To change a URL, change the route or
controller and regenerate — the Vite plugin does this on dev builds. Editing the generated
file produces a change that silently reverts.

### Never hardcode a URL

```text
import { edit } from '@/actions/App/Http/Controllers/Organizations/OrganizationController';

// correct
<Link href={edit({ organization: organization.handle })}>Settings</Link>

// wrong
<Link href={`/org/${organization.handle}/settings`}>Settings</Link>
```

Route changes should surface as TypeScript errors, not as runtime 404s. That is the entire
reason Wayfinder is in the stack.

### The UI primitives are React Aria, not Radix (ADR-015)

`components/ui/` comes from shadcn's **aria** registry (`"style": "aria-vega"`, at
`--radius: 0.875rem` — ADR-043). The props
are React Aria's, not Radix's:

| Instead of                      | Use                                                     |
| ------------------------------- | ------------------------------------------------------- |
| `onClick`                       | `onPress`                                               |
| `disabled`                      | `isDisabled`                                            |
| `open`                          | `isOpen`                                                |
| `onSelect` on menu items        | `onAction`                                              |
| `<DialogContent>`               | `<Dialog>` — it _is_ the content                        |
| `side` / `align` / `sideOffset` | `placement` (`"bottom end"`, `"right"`, …)              |
| `<SelectItem value>`            | `<SelectItem id>` + `selectedKey` / `onSelectionChange` |

Native elements keep the DOM names: a plain `<button disabled>` or `<input onClick>` is
still correct. Only React Aria components take the React Aria names.

**There is no `asChild`.** For something that navigates, in order of preference:

1. `<LinkButton href={toUrl(route())}>` — a button-shaped link.
2. `href` directly on the primitive, where it takes one: `SidebarMenuButton`,
   `DropdownMenuItem`, `BreadcrumbLink`.
3. A `render` prop, where the primitive exposes one.

`app.tsx` wires React Aria's `RouterProvider` to Inertia's router, so an `href` on any of
these performs a client-side visit. **Do not wrap them in an Inertia `<Link>`** — that is
the pattern this base exists to avoid. The trade-off is that Inertia's `prefetch` is not
available on those links; use an Inertia `<Link>` directly where prefetching genuinely
matters and the element is not a React Aria component.

Trigger components are the root of their own tree: `<DropdownMenuTrigger>` contains the
trigger _and_ the `<DropdownMenu>`; `<TooltipTrigger>` contains the trigger _and_ the
`<Tooltip>`. There is no provider to mount.

**Getting that backwards fails silently.** Writing it the Radix way — the trigger nested
inside the `<Dialog>` — compiles, type checks, lints and renders **nothing**: a closed
dialog renders none of its children, so the button that opens it never appears either. It
cost two invisible delete buttons after the React Aria migration.
`tests/Feature/DialogStructureTest.php` asserts against that shape.

A menu item cannot also be a dialog trigger. Open the dialog from state instead — see
`app-header.tsx`'s `AccountMenu` driving `CreateOrganizationModal` through `isOpen`/`onOpenChange`.

**A submit button needs `type="submit"` spelled out.** React Aria's `Button` renders
`type="button"` unless told otherwise, so a submit button written the plain HTML way — no
`type` at all — sits inside an Inertia `<Form>` and does nothing when pressed. It cost the
password-confirmation, forgot-password and resend-verification forms, all three of which
looked correct and type checked. `tests/Feature/FormSubmitButtonTest.php` asserts against
that shape by looking for `isDisabled={processing}` without `type="submit"`.

### Navigation has two levels (ADR-016, ADR-042)

| Level    | Where                               | Holds                                                                                            |
| -------- | ----------------------------------- | ------------------------------------------------------------------------------------------------ |
| Areas    | The menu bar, as a pill nav         | Tenant-scoped areas: Overview and Clients today; later Servers / Sites / DNS                     |
| Sections | The sidebar `SectionLayout` renders | The sections _of one resource or area_: a site's facilities, a client's tabs, the settings pages |

The shell is **one menu bar** and, where an area or resource has sections, **shadcn's own
`Sidebar` below it** (ADR-042). It is shadcn's `sidebar-16` block, kept structurally identical:

```text
<div className="[--header-height:calc(--spacing(14))]">   // layouts/app-layout
  <SidebarProvider className="flex flex-col">
    <AppHeader />                                          // toggle first, then a separator
    <div className="flex flex-1">                          // still layouts/app-layout
      <Sidebar className="top-(--header-height) …!" />     // layouts/section-layout
      <SidebarInset>…</SidebarInset>
```

**Do not paraphrase that frame.** The collapse animation, the persisted `sidebar_state` cookie
(read server-side in `HandleInertiaRequests`) and the mobile sheet are all the component's, and
they depend on this shape. Compare against `sidebar-16` before changing it.

The components, all reusable:

| File                      | Role                                                                                     |
| ------------------------- | ---------------------------------------------------------------------------------------- |
| `layouts/app-layout`      | The block's wrapper: `--header-height`, `SidebarProvider` stacked `flex-col`, the header |
| `shell/app-header`        | The menu bar: logo and areas left, search centred, the account menu right                |
| `shell/app-search`        | The ⌘K palette. **Destinations, not records** — extend it as resource domains are built  |
| `shell/app-logo`          | `AppLogo` (wordmark, auth pages) and `AppLogoIcon` (the mark alone, the bar)             |
| `shell/nav-tabs`          | `variant="pill"` for the bar's areas; `variant="underline"` for an in-page tab strip     |
| `ui/kbd`                  | `Kbd` and `KbdGroup`: the keycap chips in the palette footer                             |
| `layouts/section-layout`  | `Sidebar` (icon-collapsible) + the section groups + the collapse button + `SidebarInset` |
| `layouts/settings-layout` | The Settings sidebar: an Account group, then the current organization's (ADR-046)        |
| `layouts/content-layout`  | The centred `max-w-6xl` box for a page with **no** sections                              |
| `empty-state`             | Illustration, title, one sentence, one action — every list before its first record       |
| `ui/frame`                | Framed container for grouping related information: recessed frame, header, raised panels |

**The bar's right-hand control is one button, showing the active organization**, Linear-style: the
organization's avatar, then its name, in that order, styled as an ordinary `variant="outline"`
button — the same neutral, theme-following colours as any other button in the app, just pilled.
It opens `AccountMenu` in `app-header.tsx`, which carries **both** scopes in one menu rather than
splitting them across two controls: organization settings and the person at the top
(`AccountMenuContent` — avatar, name, email, Settings, Account, Theme, Log out), then a
`DropdownMenuSeparator` and "Switch organization" at the bottom. That row is a `DropdownMenuSub`,
not a flat list: its `DropdownMenuSubContent` holds the organizations you belong to — each row an
avatar with the organization's initials ahead of its name, a check beside the current one — and
"New organization" opening `CreateOrganizationModal` through `isOpen`/`onOpenChange` state, exactly
as the old `OrganizationSwitcher` did. The name no longer links to the dashboard, which the logo
and the Overview tab both still do. Below `sm` the button sheds the name and is just the avatar.

Switching tenants goes through `useSwitchOrganization`, which swaps the handle in the current URL
rather than dropping you on the new organization's dashboard.

**The palette is three surfaces, not one.** `CommandDialog` is a card whose body is a recessed
muted plate; the input sits on that plate, the results float above it on a raised `CommandPanel`,
and `CommandFooter` returns to the plate to carry the keyboard hints. The plate is the dialog's
`before` layer, so anything that must sit above it needs `relative` — `CommandPanel` has it, and a
new part on that plate will need it too. The panel bleeds past the card's side borders with
`-mx-px` plus a `clip-path`; do not "fix" either.

`CommandDialog` catches Escape in the **capture** phase. The search field consumes Escape to clear
itself and stops propagation, so the modal's own dismiss never fires — without the capture handler
the footer would promise "Esc — Close" and deliver nothing. A `CommandItem` whose label is wrapped
in an element needs an explicit `textValue`, or the filter has nothing to match and every query
returns "Nothing found".

**The second layer inside `AppLayout` is a layout, not part of it.** `app.tsx` composes
`[AppLayout, ContentLayout]` by default and `[AppLayout, SettingsLayout]` for both settings
prefixes. A new area with sections needs its own entry there and its own layout supplying the
sidebar's groups; a new area without sections needs nothing beyond `areaNavItems`.

**`SectionLayout` is the only place that may render a second-level `Sidebar`.** Two inside one
`SidebarProvider` fight over the same state. It carries the block's own
`top-(--header-height) h-[calc(100svh-var(--header-height))]!` — the container is fixed to the
viewport, so it needs the offset _and_ the height, and the `!` is the block's. Drop either and the
sidebar's first item hides under the bar. `tests/Feature/ShellStructureTest.php` asserts both.

**The sidebar collapses to an icon rail**, not to nothing: `collapsible="icon"` plus
`SidebarRail`, from `sidebar-07`. **So every section nav item needs an icon and a tooltip** — at
48px they are the whole item, and a missing one is a blank square that renders and type checks
happily. `ShellStructureTest` asserts both, and `NavItem.icon` must never be `null` in a section
layout.

**The collapse control is the last item in the sidebar's footer**, under a `SidebarSeparator`, and
it lives in `section-layout.tsx` with the sidebar it collapses. It is a `SidebarMenuButton` with an
icon and a label, so it lines up with the items above it and collapses to its icon like they do.
Its label follows the state (Collapse/Expand sidebar). It is deliberately _not_ in
`components/ui/sidebar.tsx`, where it belongs by subject: that file is regenerated by the registry
(ADR-045).

The header keeps a `SidebarTrigger` **only below `md`**, where the sidebar is a sheet with no edge
to grab, and only on pages that have a sidebar. The header sits _above_ the sidebar in the tree, so
it cannot be told by the layout below it: both read `SECTION_PAGE_PREFIXES` from
[lib/sections.ts](lib/sections.ts), and `app.tsx` keys its layout map by that type so a prefix
without a layout is a type error rather than a toggle that toggles nothing.

**One surface, not three.** `--sidebar` is `var(--background)`, so the header, the sidebar and the
content are the same colour and the hairline borders separate them (ADR-042) — that is the design.
Do not reach for a tinted sidebar or a floating panel; the inset panel, the `--panel` token and the
corner overlay that redrew its top edge behind the sticky header are gone.

**Content is boxed and centred, and the box owns the padding.** `max-w-6xl` in `AppContent`,
`max-w-4xl` in the section inset. Pages add no horizontal padding and no max-width of their own.

**Below `md` the section sidebar is a sheet.** `Sidebar` provides the sheet itself; the trigger
sits above the content in `SectionLayout`, beside the section title. The areas get the header's
own sheet, behind the hamburger.

**`SheetTrigger` is the root, like `DropdownMenuTrigger`.** It holds the trigger _and_ the
`SheetContent`. Written the Radix way — the trigger nested inside `<Sheet>` — it renders
neither, silently; that is why the old header had no mobile hamburger at all.
`tests/Feature/DialogStructureTest.php` asserts against both inversions.

A section of a single resource **never** goes in the menu bar. `SectionNav` is contextual on
purpose — different site types will present different sections, which a fixed global nav could
not express.

**Settings is one area with a group per scope (ADR-046).** `SettingsLayout` supplies both:
an **Account** group (Profile, Security) and, beneath it, the **current organization's**, labelled
with the organization's own name (General, Members, Audit log today; Roles and Billing later). The
account menu has **one** "Settings" row for the two of them, pointing at `/settings/profile`.

**The groups are one sidebar over two URL spaces**, and that is deliberate: personal settings stay
at `/settings/…` and the organization's at `/org/{organization}/settings/…` (ADR-031), each with its
own middleware and policies. The sidebar shows links; a link is not an authorisation. The
organization group is dropped when there is no current organization rather than rendered with
unbuildable hrefs.

It is still **not a pill in the menu bar** — the bar carries only Overview and Clients; a
resource-owning area earns a pill, a settings screen does not.

**`SectionLayout` takes `groups: NavGroup[]`, not a flat item list.** One group is the ordinary
case — a site will pass one, labelled with the site's name. At rail width group labels are hidden,
so the groups are separated by spacing alone and the per-item tooltips carry the labels.

**Theme lives in the avatar menu, not in Account settings** — it is a per-device display
preference, so it belongs where it can be flipped from any page. It is an ordinary
`DropdownMenuItem`, like Settings and Log out around it: the whole row toggles between light and
dark on `onAction`, not just the `Switch` riding along inside it. That `Switch` is `isReadOnly`
with its own hit-testing turned off (`pointer-events-none`), so a click on it falls through to the
row's own handler instead of firing twice. The leading icon tracks `resolvedAppearance` rather than
staying a static glyph — Sun while light is active, Moon while dark is active — so the row always
shows the theme currently in effect, not a fixed "theme" icon. There is no "System" option in this
control.

**There is no organizations list page.** Creating an organization happens in the account menu's
organizations section and deleting one on its General settings tab, so `/org` is a redirect into
the organization you are already in rather than a page. `/org/{organization}` — the bare tenant
prefix — likewise redirects to that organization's Overview; neither is ever a 404.

Adding an area means adding it to `areaNavItems` **and** to the mobile sheet in the same file;
the two do not collapse automatically on small screens.

**There are no breadcrumbs.** The menu bar has no breadcrumb row, the `breadcrumbs` prop and the
`BreadcrumbItem` type are gone, and so is `ui/breadcrumb.tsx` (ADR-045). Four pages used to declare
breadcrumbs that nothing rendered. Reintroducing them means rendering them.

**There is no alternative sidebar template.** `app-sidebar-layout` and its
`app-sidebar`/`nav-main`/`nav-footer`/`nav-user`/`user-info` components are deleted, along with the
`auth-card-layout` and `auth-split-layout` variants. Git has them if a second shell is ever
wanted; do not restore one by hand.

`ui/frame` is **hand-written, not generated**. It is not in the shadcn registry, so
`shadcn add` will not touch it — but `components/ui/` is excluded from Oxfmt
(`fmt.ignorePatterns`), so its formatting is maintained by hand. Compose with
`Frame → FrameHeader (FrameTitle, FrameDescription) → FramePanel`, and inside a panel
`FrameRow → FrameLabel + FrameControl` for label-and-control rows.

**`FrameFooter` appears only when something has changed.** Drive it from the Inertia form's
`isDirty`, with Cancel calling `reset()`. A Save button that is always visible says nothing
about whether there is anything to save, and gets ignored.

**`FrameGroup divided={false}` for rows that are one thing.** The three fields of a password
change are a single action, so they are not ruled off from each other; unrelated settings
keep the dividers.

For categories with aligned control columns — notification preferences and the like — use
`FramePanel padded={false} → FrameGroup → FrameGroupHeader (FrameGroupTitle, FrameColumn…)`
with `FrameCell` per column in each `FrameRow`. Column width comes from the
`--frame-column` variable set on the group, so the header labels and the controls beneath
them cannot drift apart; override it on the group rather than on individual cells.

### The control scale, and what `components/ui/` overwrites destroy (ADR-043, ADR-044)

The style is `aria-vega` at `--radius: 0.875rem`, with **two scales that move independently**:

- **Container spacing is Vega's, untouched** — `Card`'s `--card-spacing: 6`, the dialog's padding,
  `ui/frame`. None of them reads a control height, which is what makes the mix possible.
- **The control scale is one step tighter than Vega** (ADR-044): buttons 32/28/36/40 where Vega
  ships 36/32/40/44, inputs and selects 32, sidebar rows 28, the rail 232px not 256px. The design's
  controls measure 28–30px against a 56px header, with the same 14px text we already had.

Radius clamps move with the heights (`rounded-[min(var(--radius-md),10px)]` at 32px, `8px` at
28px), so nothing becomes a stadium at a 14px radius. **Follow that clamp in any hand-written
control** — a bare `rounded-lg` on a short row is a stadium at this radius.

`Button` carries two variants that are ours, not the registry's:

```text
<Button shape="pill" size="lg">Add client</Button>   // the one primary action of a page or card
<Button size="sm">Add client</Button>                // a toolbar action: the crisp default shape
```

`shape="pill"` is for **the single primary action of a page, card or empty state** — the full-width
auth submits and the empty state's action. Toolbar, inline and dialog buttons stay unpilled.
`shape` is declared **after** `size` so `rounded-full` beats the per-size clamps.

**`components/ui/` is generated, and re-running the registry destroys all of this.**
`shadcn apply --preset …` or `shadcn add button --overwrite` has already reverted, twice: the
`shape` and `xl` variants, the retuned scale, `SIDEBAR_WIDTH`, and `--sidebar: var(--background)`
in `app.css`. The `shape` loss breaks the build; **the rest fail silently** and the app just goes
back to feeling too big. `tests/Feature/UiVariantsTest.php` asserts each one — if it goes red after
a registry command, re-apply ADR-043 and ADR-044 rather than deleting the assertions. Re-running a
preset also re-adds duplicate `@import` lines at the top of `app.css`; de-duplicate them.

### The tenant is in the URL

Tenant-scoped routes are `/org/{organization}/…` (ADR-031). `SetOrganizationUrlDefaults` fills
it server-side, so Wayfinder helpers for organization-prefixed routes usually need no explicit organization
argument. Do not construct these URLs by hand.

### Permission booleans are for display only

```text
{permissions.canDeleteOrganization && <DeleteOrganizationModal organization={organization} />}
```

This controls what is **shown**. It is not a security control — the server re-checks the
policy on every mutating request. Hiding a button is not authorising. Never treat a prop as
permission to skip a server-side check, and never assume a hidden control cannot be invoked.

### PHP DTOs and TypeScript types are paired by hand

`resources/js/types/organizations.ts` mirrors `app/Data/UserOrganization.php` and
`app/Data/OrganizationPermissions.php`. Nothing generates one from the other, so they drift
silently. **Change both in the same commit.**

Note the existing inconsistency: `UserOrganization` serialises camelCase (`isPersonal`), while
inline controller arrays use snake_case (`role_label`). Match whatever the endpoint you are
touching already emits rather than "fixing" it in passing.

## Patterns

- Forms use `useForm` or the `<Form>` component; follow the sibling page.
- Flash messages arrive via `Inertia::flash('toast', …)` and are surfaced by `flash-toaster.tsx`,
  which both subscribes to the `flash` event and renders sonner's `Toaster`. It is mounted once, in
  `app.tsx`. Do not build a second notification path, and do not split the listener from the
  `Toaster` again — the last time, the listener lost its only caller and every flashed toast in the
  app was silently dropped. `tests/Feature/FlashToastTest.php` asserts the wiring.
- Destructive actions get a confirmation modal — see `organizations/delete-organization-modal` and
  `organizations/remove-member-modal`.
- Deferred props get a skeleton or pulsing empty state, never a bare spinner-less gap.
- Compose from `components/ui/` before writing new markup.

## Toolchain — Vite+ (`vp`)

This project uses Vite+. **Oxlint replaced ESLint and Oxfmt replaced Prettier**, and their
config lives in the `lint` and `fmt` keys of `vite.config.ts`. `eslint.config.js`,
`.prettierrc` and `.prettierignore` no longer exist — do not recreate them.

```bash
vp check          # format, lint and type check in one pass (--fix to apply)
vp lint .
vp fmt --check resources/
vp run types:check
vp dev            # or composer dev
```

`vp <name>` is a built-in; `vp run <name>` is a `package.json` script. The names overlap, so
`vp lint` and `vp run lint` are not the same thing.

A pre-commit hook runs `vp check --fix` over staged files, so formatting and lint issues are
fixed before a commit rather than in review.

Two things to leave alone in `vite.config.ts`:

- Vite plugins live inside `lazyPlugins(() => [...])`. Add new ones **inside** that callback,
  or `vp lint` and `vp fmt` have to instantiate the whole build pipeline.
- Type-aware linting depends on `baseUrl` being absent from `tsconfig.json`. Path aliasing
  works through `paths`. **Do not reintroduce `baseUrl`.**

**`vp run dev` and `composer dev` both run the full stack** — `php artisan dev`, which starts
the PHP server on `:8000`, the queue listener, Pail logs, and Vite.

**`vp dev` starts Vite alone.** Its `LARAVEL v13.21.1 … APP_URL: http://localhost:8000`
banner comes from `laravel-vite-plugin` and only echoes `APP_URL`; it starts no PHP server,
so `:8000` refuses the connection unless Herd, Valet or a separate `php artisan serve` is
handling PHP. Use it only in that case.

Run **one** stack at a time. Two concurrent `artisan dev` runs mean two Vite servers
competing for a port and overwriting each other's `public/hot`, which breaks asset loading
in ways that look random.

`composer ci:check` runs the frontend checks alongside the PHP ones and is what CI runs.

Promises must be handled. Where a hook already catches its own rejections and surfaces them
through state — as `useTwoFactorAuth` does via `errors` — mark the call `void` with a comment
saying so. Everywhere else, handle the rejection; do not silence the rule.

## Boolean data attributes

React renders `data-x={false}` as `data-x="false"` — the attribute is present, only its
value is `"false"`. Tailwind variants written as `data-x:` match on **presence**, so a
`false` still triggers them. Pass `undefined` instead:

```text
data-active={isActive || undefined}
```

This is what made every sidebar button look permanently hovered after the React Aria
migration. `data-[x=true]:` variants match on value and are safe either way — check which
form the class uses before assuming.
