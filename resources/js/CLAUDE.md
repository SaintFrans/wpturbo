# Frontend conventions (`resources/js/`)

Inertia v3 + React 19 + TypeScript + Tailwind 4. The root [CLAUDE.md](../../CLAUDE.md) has
the working method; this file covers the frontend.

Activate the `inertia-react-development` skill for Inertia client-side patterns and the
`wayfinder-development` skill when wiring frontend calls to backend routes.

## Layout

| Directory             | Contains                                                                      |
| --------------------- | ----------------------------------------------------------------------------- |
| `pages/`              | Inertia page components. Path mirrors the string in `Inertia::render()`       |
| `layouts/`            | `app/`, `auth/`, `settings/` shells                                           |
| `components/`         | Feature components (modals, `organization-switcher`)                          |
| `components/ui/`      | shadcn primitives on the React Aria base. Check here before writing a new one |
| `hooks/`              | Shared React hooks                                                            |
| `types/`              | Hand-maintained shared types                                                  |
| `actions/`, `routes/` | **Generated by Wayfinder — never hand-edit**                                  |

Files are kebab-case. Components are named exports in PascalCase.

## Non-negotiables

### Never hand-edit generated code

`actions/` and `routes/` are Wayfinder output. To change a URL, change the route or
controller and regenerate — the Vite plugin does this on dev builds. Editing the generated
file produces a change that silently reverts.

### Never hardcode a URL

```text
import { edit } from '@/actions/App/Http/Controllers/Organizations/OrganizationController';

// correct
<Link href={edit({ organization: organization.handle })}>Settings</Link>

// wrong
<Link href={`/org/${organization.handle}/settings`}>Settings</Link>
```

Route changes should surface as TypeScript errors, not as runtime 404s. That is the entire
reason Wayfinder is in the stack.

### The UI primitives are React Aria, not Radix (ADR-015)

`components/ui/` comes from shadcn's **aria** registry (`"style": "aria-vega"`). The props
are React Aria's, not Radix's:

| Instead of                      | Use                                                     |
| ------------------------------- | ------------------------------------------------------- |
| `onClick`                       | `onPress`                                               |
| `disabled`                      | `isDisabled`                                            |
| `open`                          | `isOpen`                                                |
| `onSelect` on menu items        | `onAction`                                              |
| `<DialogContent>`               | `<Dialog>` — it _is_ the content                        |
| `side` / `align` / `sideOffset` | `placement` (`"bottom end"`, `"right"`, …)              |
| `<SelectItem value>`            | `<SelectItem id>` + `selectedKey` / `onSelectionChange` |

Native elements keep the DOM names: a plain `<button disabled>` or `<input onClick>` is
still correct. Only React Aria components take the React Aria names.

**There is no `asChild`.** For something that navigates, in order of preference:

1. `<LinkButton href={toUrl(route())}>` — a button-shaped link.
2. `href` directly on the primitive, where it takes one: `SidebarMenuButton`,
   `DropdownMenuItem`, `BreadcrumbLink`.
3. A `render` prop, where the primitive exposes one.

`app.tsx` wires React Aria's `RouterProvider` to Inertia's router, so an `href` on any of
these performs a client-side visit. **Do not wrap them in an Inertia `<Link>`** — that is
the pattern this base exists to avoid. The trade-off is that Inertia's `prefetch` is not
available on those links; use an Inertia `<Link>` directly where prefetching genuinely
matters and the element is not a React Aria component.

Trigger components are the root of their own tree: `<DropdownMenuTrigger>` contains the
trigger _and_ the `<DropdownMenu>`; `<TooltipTrigger>` contains the trigger _and_ the
`<Tooltip>`. There is no provider to mount.

**Getting that backwards fails silently.** Writing it the Radix way — the trigger nested
inside the `<Dialog>` — compiles, type checks, lints and renders **nothing**: a closed
dialog renders none of its children, so the button that opens it never appears either. It
cost two invisible delete buttons after the React Aria migration.
`tests/Feature/DialogStructureTest.php` asserts against that shape.

A menu item cannot also be a dialog trigger. Open the dialog from state instead — see
`organization-switcher.tsx` driving `CreateOrganizationModal` through `isOpen`/`onOpenChange`.

**A submit button needs `type="submit"` spelled out.** React Aria's `Button` renders
`type="button"` unless told otherwise, so a submit button written the plain HTML way — no
`type` at all — sits inside an Inertia `<Form>` and does nothing when pressed. It cost the
password-confirmation, forgot-password and resend-verification forms, all three of which
looked correct and type checked. `tests/Feature/FormSubmitButtonTest.php` asserts against
that shape by looking for `isDisabled={processing}` without `type="submit"`.

### Navigation has two levels (ADR-016)

| Level    | Where                             | Holds                                                                                               |
| -------- | --------------------------------- | --------------------------------------------------------------------------------------------------- |
| Areas    | Row two of `app-header`           | Tenant-scoped areas: Overview and Settings today; later Servers / Sites / DNS. Not account settings |
| Sections | `<SectionNav>` beside the content | The sections _of one resource_: a server's facilities, an application's tabs, the settings pages    |

The shell components, all reusable:

| Component        | Role                                                                                     |
| ---------------- | ---------------------------------------------------------------------------------------- |
| `app-header`     | Row one (identity, account) and row two (areas). No breadcrumb row                       |
| `nav-tabs`       | Horizontal tabs with a sliding underline — areas, and any in-page tab strip              |
| `section-nav`    | The vertical second level: plain prefetching links, not buttons                          |
| `section-layout` | Sticky nav + centred 900px column + balancing spacer, for any area with sections         |
| `app-content`    | The inset content panel: `bg-panel`, hairline ring, rounded from `sm`                    |
| `empty-state`    | Illustration, title, one sentence, one action — every list before its first record       |
| `ui/frame`       | Framed container for grouping related information: recessed frame, header, raised panels |
| `app-footer`     | Muted footer links                                                                       |

`ui/frame` is **hand-written, not generated**. It is not in the shadcn registry, so
`shadcn add` will not touch it — but `components/ui/` is excluded from Oxfmt
(`fmt.ignorePatterns`), so its formatting is maintained by hand. Compose with
`Frame → FrameHeader (FrameTitle, FrameDescription) → FramePanel`, and inside a panel
`FrameRow → FrameLabel + FrameControl` for label-and-control rows.

**`FrameFooter` appears only when something has changed.** Drive it from the Inertia form's
`isDirty`, with Cancel calling `reset()`. A Save button that is always visible says nothing
about whether there is anything to save, and gets ignored.

**`FrameGroup divided={false}` for rows that are one thing.** The three fields of a password
change are a single action, so they are not ruled off from each other; unrelated settings
keep the dividers.

For categories with aligned control columns — notification preferences and the like — use
`FramePanel padded={false} → FrameGroup → FrameGroupHeader (FrameGroupTitle, FrameColumn…)`
with `FrameCell` per column in each `FrameRow`. Column width comes from the
`--frame-column` variable set on the group, so the header labels and the controls beneath
them cannot drift apart; override it on the group rather than on individual cells.

**The header ends with a corner overlay, and it is load-bearing.** The content panel scrolls
underneath the sticky header, which would slice its rounded top off with a hard edge. The
`aria-hidden` block at the end of `app-header` redraws the panel's top corners and top
border as part of the header, so the panel always appears to begin just below it. If you
change the panel's radius, ring colour or `--panel`, change that overlay to match.

The content panel's surface is the `--panel` token (`bg-panel`), not `bg-sidebar`: the shell
needed a surface of its own so that changing the panel does not also move the sheet and the
alternative sidebar. Dark is `#0f100f`; light is a near-white.

**Gutters are shared and must stay in step.** The header uses `px-4 sm:px-8`; the content
panel uses `sm:px-2` outside and `sm:px-6` inside, which adds up to the same `sm:px-8`.
Change one and content stops lining up with the navigation above it. Pages therefore add no
horizontal padding of their own — `AppContent` owns it.

**`SectionLayout` is the arrangement for any area with sections** — settings today, a
server or application tomorrow. Sticky nav on the left, a `max-w-[900px]` reading column,
and a spacer on the right that keeps the column centred on the page rather than pushed
right by the nav. The nav sticks below the header using `--app-header-height`, a token, so
the offset cannot drift when the header changes.

Content wider than a reading column — tables, lists — is capped at `max-w-[1092px]` inside
the 1920px container, rather than by shrinking the container.

A section of a single resource **never** goes in the top nav. `SectionNav` is contextual on
purpose — different application types will present different sections, which a fixed global
nav could not express.

**Settings is the organization's own area** (`/org/{organization}/settings`), in row two, with
`OrganizationSettingsLayout` supplying its `SectionNav`: General, Members and Audit log today,
Roles and Billing later. It earned that slot when ADR-031 made it tenant-scoped — before that it lived under
`/settings/…`, where a top-level tab would have been wrong.

**Account settings are not an area.** `AccountLayout` carries Profile and Security, reached
through the avatar menu. It is named "Account" because "Settings" now means the organization's
settings.

**Theme lives in the avatar menu, not in Account settings** — it is a per-device display
preference, so it belongs where it can be flipped from any page. It is rendered inside a
`DropdownMenuLabel`, which is the one menu slot that accepts arbitrary content; plain elements
would break React Aria's menu collection.

**There is no organizations list page.** Creating an organization happens in the header switcher
and deleting one on its General settings tab, so `/org` is a redirect into the organization you
are already in rather than a page.

Adding an area means adding it to `areaNavItems` **and** to the mobile sheet in the same
file; the two levels do not collapse automatically on small screens.

**Breadcrumbs are not rendered.** The header has no breadcrumb row. Pages still declare
`breadcrumbs` in their `.layout` block and `AppLayout` still accepts the prop, because the
alternative sidebar template renders them — so setting them changes nothing under the
current layout. Do not spend time on breadcrumb copy expecting it to appear.

`layouts/app/app-sidebar-layout.tsx` and its `app-sidebar`/`nav-main`/`nav-footer`
components remain as the alternative template. They are not in use — do not add navigation
to them and expect it to appear.

### The tenant is in the URL

Tenant-scoped routes are `/org/{organization}/…` (ADR-031). `SetOrganizationUrlDefaults` fills
it server-side, so Wayfinder helpers for organization-prefixed routes usually need no explicit organization
argument. Do not construct these URLs by hand.

### Permission booleans are for display only

```text
{permissions.canDeleteOrganization && <DeleteOrganizationModal organization={organization} />}
```

This controls what is **shown**. It is not a security control — the server re-checks the
policy on every mutating request. Hiding a button is not authorising. Never treat a prop as
permission to skip a server-side check, and never assume a hidden control cannot be invoked.

### PHP DTOs and TypeScript types are paired by hand

`resources/js/types/organizations.ts` mirrors `app/Data/UserOrganization.php` and
`app/Data/OrganizationPermissions.php`. Nothing generates one from the other, so they drift
silently. **Change both in the same commit.**

Note the existing inconsistency: `UserOrganization` serialises camelCase (`isPersonal`), while
inline controller arrays use snake_case (`role_label`). Match whatever the endpoint you are
touching already emits rather than "fixing" it in passing.

## Patterns

- Forms use `useForm` or the `<Form>` component; follow the sibling page.
- Flash messages arrive via `Inertia::flash('toast', …)` and are surfaced by
  `use-flash-toast`, rendered with `sonner`. Do not build a second notification path.
- Destructive actions get a confirmation modal — see `delete-organization-modal`,
  `remove-member-modal`, `leave-organization-modal`.
- Deferred props get a skeleton or pulsing empty state, never a bare spinner-less gap.
- Compose from `components/ui/` before writing new markup.

## Toolchain — Vite+ (`vp`)

This project uses Vite+. **Oxlint replaced ESLint and Oxfmt replaced Prettier**, and their
config lives in the `lint` and `fmt` keys of `vite.config.ts`. `eslint.config.js`,
`.prettierrc` and `.prettierignore` no longer exist — do not recreate them.

```bash
vp check          # format, lint and type check in one pass (--fix to apply)
vp lint .
vp fmt --check resources/
vp run types:check
vp dev            # or composer dev
```

`vp <name>` is a built-in; `vp run <name>` is a `package.json` script. The names overlap, so
`vp lint` and `vp run lint` are not the same thing.

A pre-commit hook runs `vp check --fix` over staged files, so formatting and lint issues are
fixed before a commit rather than in review.

Two things to leave alone in `vite.config.ts`:

- Vite plugins live inside `lazyPlugins(() => [...])`. Add new ones **inside** that callback,
  or `vp lint` and `vp fmt` have to instantiate the whole build pipeline.
- Type-aware linting depends on `baseUrl` being absent from `tsconfig.json`. Path aliasing
  works through `paths`. **Do not reintroduce `baseUrl`.**

**`vp run dev` and `composer dev` both run the full stack** — `php artisan dev`, which starts
the PHP server on `:8000`, the queue listener, Pail logs, and Vite.

**`vp dev` starts Vite alone.** Its `LARAVEL v13.21.1 … APP_URL: http://localhost:8000`
banner comes from `laravel-vite-plugin` and only echoes `APP_URL`; it starts no PHP server,
so `:8000` refuses the connection unless Herd, Valet or a separate `php artisan serve` is
handling PHP. Use it only in that case.

Run **one** stack at a time. Two concurrent `artisan dev` runs mean two Vite servers
competing for a port and overwriting each other's `public/hot`, which breaks asset loading
in ways that look random.

`composer ci:check` runs the frontend checks alongside the PHP ones and is what CI runs.

Promises must be handled. Where a hook already catches its own rejections and surfaces them
through state — as `useTwoFactorAuth` does via `errors` — mark the call `void` with a comment
saying so. Everywhere else, handle the rejection; do not silence the rule.

## Boolean data attributes

React renders `data-x={false}` as `data-x="false"` — the attribute is present, only its
value is `"false"`. Tailwind variants written as `data-x:` match on **presence**, so a
`false` still triggers them. Pass `undefined` instead:

```text
data-active={isActive || undefined}
```

This is what made every sidebar button look permanently hovered after the React Aria
migration. `data-[x=true]:` variants match on value and are safe either way — check which
form the class uses before assuming.
